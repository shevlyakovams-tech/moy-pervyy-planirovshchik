# Техническое задание: «Сначала — ты»

**Версия документа:** 1.3

**Дата фиксации требований:** 14.08.2026

**Дата последней редакции:** 22.08.2026

**Статус:** утверждённые требования к MVP

**Формат продукта:** локальное однопользовательское приложение для Windows 10/11 и отдельная статическая браузерная редакция для GitHub Pages
**Название продукта:** «Сначала — ты»

**Слоган:** «Потом — всё остальное.»

> «Сначала — ты» — личный ежедневник в форме книжных разворотов. Он помогает взрослому человеку утром выбрать главное на день, связать день с целью недели, оставить место для себя и близких и мягко отслеживать привычки без наказаний за пропуски.

### Дополнение версии 1.3: публичная браузерная редакция

- браузерная редакция публикуется как статическое приложение на GitHub Pages без удалённого сервера, регистрации и облачной базы;
- все личные записи хранятся только в локальном хранилище текущего профиля браузера и не загружаются в GitHub;
- при первом открытии на каждом новом компьютере или в новом профиле браузера автоматически запускается первоначальное знакомство;
- данные между компьютерами и профилями браузера не синхронизируются;
- очистка данных сайта в браузере удаляет локальные записи и возвращает первоначальное знакомство;
- исходный код публикуется в новом публичном GitHub-репозитории владельца, основная ветка называется `main`;
- браузерная редакция сохраняет продуктовые сценарии ежедневника, недели, задач, привычек, прогресса, архива и настроек;
- системный трей, автозапуск Windows и фоновые уведомления закрытого браузера остаются функциями Windows-редакции и не имитируются на GitHub Pages;
- обычная работа браузерной редакции не выполняет внешних запросов после загрузки статических файлов, кроме явного перехода пользователя к источнику цитаты;
- публикация считается завершённой только после проверки чистого первого запуска, локального сохранения после перезагрузки, изоляции данных между двумя браузерными профилями и открытия публичной HTTPS-ссылки.

9. Приложение Б имеет справочный, ненормативный статус и не создаёт требований к коду.

## 2. Цель продукта

### 2.1. Главная цель

Научить пользователя:

- выбирать один главный результат дня и не более трёх приоритетных задач;
- связывать ежедневные действия с одной целью недели;
- сознательно оставлять время для себя и близких;
- разгружать список задач без автоматического переноса и чувства вины;
- внедрять привычки в обычную жизнь через наблюдение за фактическим прогрессом.

### 2.2. Проблемы, которые решает продукт

- прокрастинация;
- перегруз большим количеством задач;
- трудность выбора главного;
- хаотичное планирование;
- отсутствие времени для личных желаний и общения с близкими;
- нерегулярное выполнение привычек;
- демотивация из-за жёстких серий, баллов и наказаний.

### 2.3. Целевая аудитория

Один взрослый пользователь любого взрослого возраста, который понимает свои цели, но нуждается в спокойной структуре для ежедневных решений. Детский режим, родительский контроль и адаптация для организаций в MVP не предусмотрены.

Следует различать продуктовую аудиторию и оператора текущей версии:

- **продуктовая аудитория** — взрослый человек, которому нужна спокойная помощь с приоритетами, временем для себя и привычками;
- **оператор локального MVP 1.2** — владелец проекта, способный один раз выполнить setup.bat, при необходимости установить Node.js LTS по инструкции и затем запускать start.bat;
- MVP 1.2 является внутренним личным прототипом и не заявляется как готовый способ распространения приложения среди нетехнических пользователей;
- перед публичным выпуском потребуется отдельный этап упаковки с обычной установкой без ручной работы с Node.js, npm и командной строкой.

### 2.4. Критерии продуктового успеха MVP

MVP считается полезным, если после личного тестирования пользователь:

- может завершать утреннее планирование, назначив хотя бы одну задачу дня № 1;
- видит цель недели на ежедневном развороте;
- регулярно фиксирует минимум одну из поддерживаемых привычек;
- может отличить важные задачи от необязательных;
- не воспринимает пропуск как наказание со стороны интерфейса;
- может восстановить картину прошедших дней через архив и поиск.

Это продуктовые ориентиры, а не автоматически рассчитываемый «балл успеха».

Продуктовый успех и техническая приёмка не заменяют друг друга: личное тестирование отвечает на вопрос о полезности, а критерии раздела 37 — на вопрос о соответствии реализации зафиксированному поведению.

## 3. Границы MVP

### 3.1. В MVP обязательно входят

- одноразовое первоначальное знакомство;
- книжный интерфейс с разворотами;
- экран сегодняшнего дня;
- навигация по календарным датам;
- утренняя рефлексия, благодарность, настроение, мысль и настрой дня;
- один главный результат дня;
- от одной до трёх задач дня с внутренними рангами приоритета 1–3;
- обычные задачи пяти фиксированных категорий;
- отдельные действия «Для себя» и «Для других»;
- недельное планирование с одной целью и тремя шагами;
- встроенная проверенная библиотека из 60 цитат;
- избранные и скрытые цитаты;
- простые пользовательские привычки-флажки;
- встроенный таймер планки;
- встроенный счётчик подходов отжиманий;
- встроенный трекер воды;
- статистика за неделю, месяц и всё время;
- архив дней и недель;
- полнотекстовый поиск по согласованным типам записей;
- локальные фоновые уведомления, системный трей и опциональный автозапуск;
- локальная SQLite-база и миграции без потери данных;
- setup.bat, start.bat и README.md;
- полное удаление личных данных с повторным запуском знакомства.

### 3.2. В MVP не входят

- регистрация, вход, роли, PIN-код и пароль;
- несколько пользователей;
- облачная синхронизация;
- резервное копирование;
- экспорт или импорт;
- восстановление удалённых данных;
- публичный профиль;
- социальные функции, соревнования и сравнение с другими;
- подписки и платежи;
- мобильное нативное приложение;
- установщик EXE или MSI;
- Docker;
- тёмная тема;
- пользовательские цветовые темы;
- новые пользовательские категории задач;
- пользовательские числовые или таймерные типы привычек;
- произвольные диапазоны статистики и сравнение периодов;
- проекты, подзадачи, вложения, файлы, заметки к задачам, дедлайны и оценка длительности;
- месячные, квартальные и годовые цели;
- искусственный интеллект, советы «от психолога» и автоматический анализ текста;
- медицинская диагностика и нормы воды, спорта или нагрузки;
- заимствованные тексты, страницы, название или графика книги «6 минут»;
- телеметрия, внешняя аналитика и рекламные SDK.

## 4. Акторы и права

### 4.1. Пользователь

Единственный владелец локального экземпляра приложения. Может:

- проходить или пропускать знакомство;
- создавать и изменять записи в разрешённых датах;
- планировать текущие и будущие задачи;
- управлять недельными целями;
- создавать простые привычки;
- включать встроенные трекеры;
- фиксировать прогресс текущего дня;
- просматривать статистику и архив;
- управлять уведомлениями;
- удалять все личные данные.

### 4.2. Фоновый процесс

Локальный технический актор. Может:

- запускать локальный сервер;
- держать приложение доступным после закрытия браузера;
- планировать и показывать уведомления;
- поддерживать значок в системном трее;
- открывать приложение по действию пользователя;
- выполнять переход суток и технические миграции;
- записывать обезличенные технические ошибки.

Фоновый процесс не анализирует содержание личных записей и не отправляет данные наружу.

### 4.3. Отсутствующие акторы

В MVP нет гостя, администратора, модератора, тренера, врача, психолога, другого пользователя или удалённого сервера.

### 4.4. Роли проекта и приёмка

- владелец продукта — пользователь проекта; он единолично утверждает изменения продуктового поведения и принимает итоговый MVP;
- разработчик реализует требования, выполняет проверки и сообщает об обнаруженном противоречии, но не расширяет продукт по собственной инициативе;
- техническая приёмка выполняется по обязательным AC, P0-тестам и Definition of Done;
- продуктовая приёмка выполняется владельцем после личного прохождения основных сценариев на своих данных;
- окончательная готовность фиксируется только при одновременной технической и продуктовой приёмке;
- календарные сроки, оценка трудозатрат, бюджет, оплата и коммерческий состав команды не являются частью этого технического задания и при необходимости планируются отдельно.

## 5. Продуктовые принципы

### 5.1. Мягкая мотивация

Допустимые формулировки:

- «Одной важной задачи уже достаточно, чтобы у дня появилось направление».
- «Сегодня без отметки — продолжить можно в следующий запланированный день».
- «Пока нет данных. Они появятся после первой записи».
- «Можно сделать проще».

Запрещены:

- «Вы сорвали серию»;
- «Вы ленились»;
- «Плохой результат»;
- «Нужно наверстать»;
- красные наказующие экраны;
- сравнение пользователя с другими;
- общий балл продуктивности;
- психологические выводы по настроению или тексту.

### 5.2. Достаточность одной задачи

Утреннее планирование разрешено завершить при наличии одной непустой задачи дня № 1. Задачи дня № 2 и № 3 рекомендуются, но не обязательны. Все поля, кроме задачи дня № 1, могут быть пустыми.

### 5.3. Утро — основной ритуал

Основной сценарий выполняется утром. Днём пользователь может отмечать задачи и привычки. Обязательного вечернего ритуала нет.

Длительность ритуала не фиксируется и не измеряется. В интерфейсе нет цели «6 минут», обратного отсчёта или награды за скорость: пользователь может потратить 2, 3, 5, 15 минут или столько, сколько ему удобно.

### 5.4. Прогресс — факт, а не оценка личности

Приложение показывает даты, количества, суммы, проценты и серии. Оно не делает выводов о характере, силе воли, психическом состоянии или ценности пользователя.

### 5.5. Оригинальность

Книжная метафора и идея короткого ритуала допустимы как вдохновение. Тексты вопросов, структура, название, графика и формулировки продукта должны быть оригинальными.

## 6. Платформа и техническая архитектура

### 6.1. Целевая среда

- Windows 10 и Windows 11;
- актуальные стабильные Chrome и Microsoft Edge;
- ширина окна от 360 до 1920 пикселей;
- один локальный компьютер;
- системный формат времени 24 часа;
- язык интерфейса — русский;
- формат отображения даты — ДД.ММ.ГГГГ;
- неделя всегда начинается в понедельник.

### 6.2. Обязательный технологический стек

- интерфейс и локальный HTTP-сервер: Next.js с App Router;
- язык: TypeScript в строгом режиме;
- UI: React;
- база: SQLite;
- ORM и миграции: Prisma;
- проверка входных данных: Zod;
- перетаскивание задач: @dnd-kit/core и @dnd-kit/sortable;
- графики: Recharts;
- тесты модулей: Vitest;
- тесты компонентов: Testing Library;
- сквозные тесты: Playwright;
- локальный процесс-руководитель и трей: Electron main process.

Все зависимости входят в локальную сборку. CDN, удалённые шрифты и внешние API запрещены.

Точные версии берутся как последние совместимые стабильные, не canary и не beta, на дату начала разработки, затем фиксируются в package-lock.json. После фиксации обновление версии не должно происходить неявно.

### 6.3. Состав процессов

#### 6.3.1. Основной профиль production-сборки

1. В next.config.ts обязательно задаётся output: "standalone".
2. После next build скрипт сборки копирует каталог public, если он существует, в .next/standalone/public.
3. Каталог .next/static копируется в .next/standalone/.next/static.
4. Скрипт проверяет наличие .next/standalone/server.js, статических ресурсов, Prisma Client и всех runtime-артефактов, требуемых зафиксированной версией Prisma для SQLite.
5. NEXT_TELEMETRY_DISABLED устанавливается в 1 при сборке и запуске.
6. Сборка не обращается к CDN и не ожидает внешних ресурсов во время работы.

#### 6.3.2. Последовательность запуска

1. Electron main process получает блокировку единственного экземпляра.
2. Он проверяет наличие production-сборки, каталога данных и применимость схемы базы.
3. Он убеждается, что 127.0.0.1:3210 свободен либо уже принадлежит подтверждённому экземпляру этого приложения.
4. Он запускает отдельный дочерний процесс Node.js командой node server.js с рабочим каталогом .next/standalone. Эквивалентный запуск из корня проекта — node .next/standalone/server.js.
5. Дочернему процессу передаются HOSTNAME=127.0.0.1, PORT=3210, DATABASE_URL с абсолютным путём к локальной SQLite-базе и NEXT_TELEMETRY_DISABLED=1.
6. Electron опрашивает GET /api/health каждые 250 мс не более 15 секунд. Успехом считается HTTP 200 с status = "ok", совпадающей appVersion и ожидаемой schemaVersion; ответ не содержит личных данных.
7. Только после успешной проверки Electron создаёт трей, запускает планировщик уведомлений и открывает адрес в браузере по умолчанию. При системном автозапуске браузер не открывается.
8. Закрытие вкладки браузера не завершает Electron и локальный сервер.
9. Команда «Выход» в трее останавливает планировщик, просит дочерний процесс корректно завершиться, ждёт не более 5 секунд и при необходимости завершает только известный дочерний PID.

Дочерний процесс запускается с windowsHide = true и detached = false. Его stdout и stderr направляются в фильтрованный технический журнал по правилам раздела 32; личный текст и полные SQL-параметры туда не попадают.

Если сервер неожиданно завершился, Electron подавляет зависящие от него уведомления и выполняет одну попытку перезапуска через 1 секунду. Если повторный запуск не прошёл health-check, бесконечного цикла нет: в трее показывается состояние ошибки, пользователь получает нейтральное техническое сообщение, а подробности без личных данных записываются в журнал.

Если второй запуск обнаруживает уже работающий экземпляр, он только открывает существующее приложение и завершается.

Если порт 3210 занят посторонним процессом, приложение не выбирает случайный порт: показывает понятное техническое сообщение, пишет безопасную запись в журнал и не подключается к неизвестному серверу.

#### 6.3.3. Резервный технический профиль

Если официальный standalone-профиль несовместим с зафиксированной версией Next.js или Prisma, разработчик может до приёмки переключить реализацию на локальный next start, запускаемый из уже установленного node_modules. Для такой сборки output: "standalone" отключается: одновременно использовать next start и standalone-сборку нельзя. Это не автоматический runtime-fallback и не пользовательская настройка. Резервный профиль обязан слушать только 127.0.0.1:3210, работать офлайн и пройти те же AC-START, AC-MIG и тесты фонового процесса. Смена профиля фиксируется в истории версии ТЗ или в принятом техническом решении по правилам раздела 44.

Техническое основание основного профиля: [официальное описание Next.js output: standalone](https://nextjs.org/docs/15/app/api-reference/config/next-config-js/output). Если адрес документации изменится, это не меняет зафиксированное поведение сборки.

### 6.4. Интерактивные уведомления

Для гарантированной работы кнопок «Открыть», «Отложить на 15 минут» и «Закрыть» разрешено использовать небольшое локальное toast-окно Electron. Оно оформляется как системное уведомление, не требует открытого браузера и не содержит личных текстов. Использование внешнего сервиса уведомлений запрещено.

### 6.5. Локальные каталоги

Личные файлы не хранятся в Git-репозитории. Используются:

- база: %LOCALAPPDATA%\UtrenniyRazvorot\data\app.db;
- журнал: %LOCALAPPDATA%\UtrenniyRazvorot\logs\app.log;
- технические настройки запуска: %LOCALAPPDATA%\UtrenniyRazvorot\config.

Каталоги создаются автоматически. Путь к базе задаётся одной переменной окружения приложения, которую формирует start.bat или Electron-процесс; пользователь не должен настраивать её вручную.

### 6.6. Сетевые ограничения

- сервер слушает только 127.0.0.1, а не 0.0.0.0;
- обычная работа не выполняет HTTP-запросы во внешнюю сеть;
- все шрифты, иконки, звуки и цитаты поставляются локально;
- ссылка на источник цитаты открывается только после нажатия «Источник» и затем явного нажатия на ссылку;
- отсутствие интернета не вызывает ошибок на основных экранах.

## 7. Установка, сборка и запуск

### 7.1. setup.bat

Файл обязан:

1. Проверить Windows и доступность совместимой версии Node.js LTS и npm.
2. Если Node.js отсутствует, показать понятную инструкцию и официальный адрес загрузки; автоматически устанавливать Node.js и требовать права администратора не нужно.
3. Если приложение запущено, остановить настройку с просьбой завершить его через трей; менять файлы активного экземпляра запрещено.
4. Выполнить npm ci строго по package-lock.json.
5. Сгенерировать Prisma Client.
6. Собрать production-версию Next.js в standalone-профиле и Electron main process.
7. Скопировать локальные статические ресурсы по правилам 6.3.1.
8. Проверить новую сборку и все миграции на временной пустой базе; реальные пользовательские данные на этом шаге не затрагиваются.
9. Проверить, что версия кода не ниже уже записанных appVersion, schemaVersion и seedVersion; downgrade автоматически запрещён.
10. Применить к реальной базе только поставленные с этой версией миграции командой prisma migrate deploy.
11. Идемпотентно добавить встроенные вопросы и 60 цитат.
12. Выполнить integrity_check, проверить контрольные суммы seed и коротко запустить health-check новой сборки.
13. Записать успешные appVersion, schemaVersion и seedVersion в AppMetadata и атомарно создать build-manifest.json только после прохождения всех предыдущих шагов.
14. Завершиться с кодом 0 только при полном успехе; при ошибке вернуть ненулевой код и не показывать сообщение об успешной настройке.

Интернет требуется при первой загрузке Node.js и npm-зависимостей, а также может потребоваться при ручном обновлении, если новая версия меняет зависимости и нужных пакетов нет в локальном npm-кэше. После успешного setup.bat обычная работа не требует интернета.

### 7.2. start.bat

Файл обязан:

1. Работать без интернета после успешного setup.bat.
2. Проверять наличие сборки, базы и созданного setup.bat файла build-manifest.json с appVersion, schemaVersion и seedVersion.
3. Если версия исходного package.json отличается от build-manifest.json, не запускать устаревшую сборку и предложить выполнить setup.bat.
4. Применять только ожидающие миграции, поставленные и проверенные вместе с той же appVersion сборки; downgrade и неизвестная миграция блокируют запуск.
5. Никогда не выполнять npm ci, next build или изменение seed: это обязанности setup.bat.
6. Запускать Electron-процесс без видимого окна консоли либо сворачивать техническое окно.
7. Открывать приложение в Chrome или Edge через системный браузер по умолчанию.
8. Не создавать второй сервер, если экземпляр уже запущен.

### 7.5. Обновление существующей локальной версии

Автоматического обновления и удалённого канала доставки в MVP нет. Получение новых исходных файлов выполняется владельцем отдельно и не является функцией приложения.

Обязательный порядок обновления на том же компьютере:

1. Завершить приложение через меню трея и убедиться, что Electron и дочерний сервер остановлены.
2. Заменить исходные файлы на новую согласованную версию, сохранив каталог %LOCALAPPDATA%\UtrenniyRazvorot без изменений.
3. Запустить setup.bat; простой запуск start.bat не заменяет сборку новой версии.
4. setup.bat сначала собирает и проверяет код на временной базе и только затем применяет миграции к реальной базе.
5. При ошибке до миграции существующая база не меняется. При ошибке миграции действует транзакционный запрет частичного состояния из раздела 33, запуск новой версии блокируется, база не очищается.
6. После успешной настройки запустить start.bat и проверить appVersion и schemaVersion на экране настроек.

Правила совместимости:

- пользовательская база всегда остаётся по постоянному пути из 6.5 и не хранится внутри каталога сборки;
- обновление не удаляет дневник, задачи, недельные планы, привычки, измерения, избранное, скрытие и настройки;
- автоматический downgrade приложения или схемы запрещён;
- повторный запуск setup.bat для той же версии идемпотентен;
- автоматическая резервная копия перед обновлением не создаётся по решению MVP; связанный риск явно принят в разделе 43;
- README содержит этот порядок дословно и перечисляет сообщения об ошибках несовместимой Node.js, неуспешной сборки, миграции и health-check.

## 9. Единые правила дат, времени и блокировки

### 9.1. Бизнес-дата

Бизнес-дата вычисляется по локальным часам Windows. В базе календарная дата хранится строкой формата YYYY-MM-DD, отдельно от временной метки UTC.

Историческая запись не меняет дату при смене часового пояса или переводе часов.

AppMetadata хранит maxObservedBusinessDate. Эффективная бизнес-дата не может стать меньше уже наблюдавшейся даты: если системные часы переведены назад, приложение использует maxObservedBusinessDate, показывает предупреждение о часах и не разблокирует прошлые записи.

### 9.2. Состояния даты

| Состояние | Условие | Права |
|---|---|---|
| Сегодня | дата равна локальной системной дате | полный ввод дня, задач и привычек |
| Прошлое | дата меньше локальной системной даты | только чтение, кроме специальных действий разбора незавершённых задач |
| Будущее | дата больше локальной системной даты | добавление обычных задач только с названием и категорией |

### 9.3. Что разрешено в будущем

- открыть любую будущую дату;
- добавить, изменить, удалить и переставить обычные задачи;
- указать только название и одну из пяти категорий;
- открыть любую будущую неделю;
- заполнить цель недели и три шага.

До наступления даты запрещены:

- главный результат дня;
- ранг приоритета;
- действия «Для себя» и «Для других»;
- благодарность;
- настроение и заметка к нему;
- мысль и настрой;
- ответы на вопросы;
- цитата дня;
- отметки и измерения привычек;
- кнопка «Завершить».

### 9.4. Что запрещено в прошлом

После смены даты нельзя:

- изменять тексты дневника;
- добавлять или удалять дневную запись;
- изменять приоритеты;
- добавлять задачи задним числом;
- редактировать измерения привычек;
- выбирать другую цитату;
- менять настроение.

Разрешены только явно описанные действия разбора незавершённых задач и незавершённых недельных целей.

### 9.5. Переход в полночь

Если приложение открыто при смене даты:

1. Все успешно введённые данные текущего дня немедленно сохраняются.
2. Незавершённый таймер планки и трёхсекундный отсчёт отменяются без записи результата.
3. Прошедший день становится только для чтения.
4. Простые привычки без отметки и числовые привычки ниже цели фиксируются как пропущенные только для расчётов; отдельная пустая запись не создаётся.
5. Показывается модальное сообщение «Наступил новый день».
6. После подтверждения открывается сегодняшний разворот.

Если приложение не работало в полночь, те же вычисляемые состояния определяются при следующем запуске.

### 9.6. Пропущенный день

Если приложение в дату не открывалось:

- DailyEntry автоматически не создаётся;
- цитата не считается показанной;
- настроение отсутствует;
- ответы и тексты отсутствуют;
- в архиве показывается «Нет записи»;
- запланированные привычки после полуночи считаются пропущенными для статистики без создания фиктивного HabitLog.

## 10. Сохранение, ограничения текста и ошибки

### 10.1. Автосохранение

- текст сохраняется через 600 мс после последнего изменения и при потере фокуса;
- переключатель, настроение, порядок и статус сохраняются немедленно;
- одновременно для одного поля отправляется не более одного запроса; более новое значение ставится в очередь;
- интерфейс показывает «Сохранение…», «Сохранено» или «Не удалось сохранить»;
- перед навигацией и действием «Завершить» очередь сохранения должна быть сброшена;
- при ошибке данные остаются в поле и предлагается «Повторить»;
- успешное уведомление не показывается всплывающим окном при каждом сохранении.

### 10.2. Общая нормализация

- пробелы по краям удаляются;
- последовательности пробелов в однострочном названии сводятся к одному;
- пустая строка сохраняется как null;
- управляющие символы удаляются, переносы строк разрешены только в многострочных полях;
- HTML пользователя отображается как текст и никогда не исполняется;
- все ограничения повторяются на сервере, клиентская проверка не считается достаточной.

### 10.3. Лимиты

| Поле | Ограничение |
|---|---:|
| Название задачи | 1–240 символов |
| Название простой привычки | 1–80 символов |
| Главный результат дня | до 500 символов |
| Действие для себя или других | до 500 символов |
| Благодарность, мысль, настрой | до 2000 символов каждое |
| Ответ на вопрос | до 2000 символов |
| Заметка к настроению | до 500 символов |
| Цель недели | до 500 символов |
| Почему цель важна, критерий, препятствие, запасной план | до 2000 символов каждое |
| Шаг недели | до 500 символов |

После 80 процентов лимита показывается спокойный счётчик символов.

## 11. Первоначальное знакомство

### 11.1. Общие требования

- показывается один раз после первого запуска или полного удаления данных;
- каждый шаг можно пропустить;
- можно пропустить всё знакомство;
- назад можно вернуться до завершения;
- промежуточные значения сохраняются локально;
- пропуск не создаёт фиктивных записей;
- тон дружелюбный, вежливый, без фамильярности.

### 11.2. Последовательность

1. **Добро пожаловать.** Главный заголовок: «Сначала — ты. Потом — всё остальное.» Коротко объяснить: цель сервиса — услышать себя, выбрать главное, оставить место для себя и близких, видеть прогресс без давления. Основная кнопка называется «Начать знакомство».
2. **День недельного планирования.** Выбор дня недели; при пропуске — воскресенье.
3. **Первая цель недели.** Необязательная цель текущей недели.
4. **Встроенные трекеры.** Независимые переключатели «Планка», «Отжимания», «Вода».
5. **Параметры выбранных трекеров.** Цель и конкретные дни недели; для воды — личная цель в миллилитрах без предлагаемой медицинской нормы.
6. **Простая привычка.** Необязательное название и дни недели.
7. **Завершение.** Кнопка «Перейти к сегодняшнему дню».

### 11.3. Результаты пропуска

- если день планирования пропущен, используется воскресенье;
- если все привычки пропущены, список привычек пуст;
- ни один встроенный трекер не включается автоматически;
- привычка без цели или расписания сохраняется как черновик и не показывается на «Сегодня»;
- пустая недельная цель не создаёт содержательную запись недели.

2. «Что осталось незавершённым и по-прежнему действительно важно?»
3. «Что я могу сегодня сделать немного проще или лучше?»

Ответы всегда необязательны.

### 12.3. Меняющиеся вопросы

Встроенный список:

1. «Что вчера дало мне энергию?»
2. «Что забрало у меня больше всего сил?»
3. «Удалось ли мне уделить время себе?»
4. «Как я проявил внимание к близкому человеку?»
5. «За что я могу поблагодарить себя?»
6. «Какой момент вчерашнего дня я хочу запомнить?»
7. «Что я понял о себе?»
8. «От какой необязательной задачи я могу отказаться?»
9. «Где я взял на себя больше, чем мог выполнить?»
10. «Какой небольшой выбор приблизил меня к цели недели?»

Алгоритм выбора: циклическая перемешанная колода; один вопрос на фактически открытый день; в пределах цикла повторов нет; вопрос сохраняется в DailyEntry и не меняется при повторном открытии.

### 12.4. Настроение

Ровно пять значений:

1. Тяжело
2. Ниже обычного
3. Ровно
4. Хорошо
5. Отлично

Значение необязательно. Рядом доступна необязательная заметка. Интерфейс не интерпретирует настроение и не предлагает диагнозов или советов.

### 12.5. Правая страница «Выбрать главное»

Порядок блоков:

1. цель недели;
2. задачи дня № 1–3;
3. остальные задачи по категориям;
4. действие «Для себя»;
5. действие «Для других»;
6. главный результат дня;
7. привычки, запланированные на сегодня.

Главный результат — отдельный текст, а не задача и не категория. Для него нет статуса выполнения в MVP.

### 12.6. Завершение утреннего планирования

- пользовательская кнопка называется «Завершить»;
- видна и активна только на сегодняшней дате;
- активна, когда существует минимум одна непустая задача с priorityRank 1 и статусом planned или completed;
- если задачи дня № 1 нет, кнопка неактивна и рядом текст: «Перед завершением выберите одну главную задачу дня»;
- нажатие сначала завершает все ожидающие сохранения;
- затем записывает morningCompletedAt;
- кнопка меняется на спокойный статус «Завершено» с поддерживающей фразой «Ты молодец!»;
- нейтральная пользовательская надпись «Завершено» означает завершение утреннего планирования, а не ручное закрытие календарного дня;
- завершение не блокирует сегодняшний день: до полуночи его можно редактировать;
- при завершённом утреннем планировании нельзя удалить, перенести, отметить «Не актуально» или снять приоритет с последней действующей задачи дня № 1, пока другой задаче не назначен ранг 1.

Отдельной кнопки «Завершить день» нет. День закрывается автоматически при смене даты.

### 12.7. Отметки действий для себя и других

У каждого из двух текстов есть независимый флажок выполнения, доступный только сегодня. Флажок показывается, если текст непустой. Он нужен для статистики количества дней с выполненным действием. В прошлом флажок только читается.

## 13. Задачи

### 13.1. Фиксированные категории

Ровно пять:

- Работа
- Близкие
- Семья
- Хобби
- Обучение

Пользователь не может добавлять, переименовывать, скрывать или удалять категории. «Для себя» не является категорией.

### 13.2. Поля задачи

| Поле | Обязательность | Правило |
|---|---|---|
| Название | обязательно | 1–240 символов |
| Дата | обязательно | сегодня или будущее при создании |
| Категория | обязательно | одно из пяти значений |
| Ранг приоритета | необязательно | 1, 2 или 3; только сегодня |
| Статус | обязательно | planned, completed, transferred, let_go |
| Порядок | автоматически | целое число внутри даты и блока |
| Источник переноса | автоматически | ссылка на исходную задачу |

В задаче нет времени, длительности, отдельного дедлайна, заметки, подзадач, проекта и вложения.

### 13.3. Приоритеты

- на одну дату может быть не более одной задачи каждого ранга 1, 2 и 3;
- пользовательский список назначения содержит ровно четыре подписи: «Без приоритета», «Задача дня № 1», «Задача дня № 2», «Задача дня № 3»;
- ранг 1, отображаемый как «Задача дня № 1», обязателен только для действия «Завершить»;
- при назначении занятого ранга задачи меняются местами;
- перетаскивание внутри блока меняет ранги;
- снятая с приоритета задача остаётся обычной задачей;
- transferred и let_go с сохранённым рангом не удовлетворяют условию завершения утреннего планирования;
- будущей задаче ранг назначить нельзя до наступления даты.

### 13.4. Статусы

| Статус | Значение |
|---|---|
| planned | запланирована и ещё не разобрана |
| completed | выполнена в привязанную календарную дату |
| transferred | вместо неё создана новая задача на другую дату |
| let_go | пользователь сознательно отказался от задачи |

Автоматического переноса нет.

### 13.5. Действия сегодня

Пользователь может:

- создать задачу;
- изменить название и категорию;
- назначить или изменить приоритет;
- переставить задачи;
- отметить выполненной;
- вернуть выполненную в planned до полуночи;
- удалить текущую planned-задачу;
- перенести planned-задачу на будущую дату;
- выбрать «Не актуально».

При переносе исходная получает transferred, новая — planned, ту же категорию и название, sourceTaskId исходной, без приоритета. Исходная и новая показывают ненавязчивую связь в архиве.

После успешного переноса в блоке задач показывается спокойное подтверждение «Задача перенесена на <дата>». Перенесённая задача исчезает из активного списка исходной даты и появляется на выбранной дате.

### 13.6. Действия с будущими задачами

До наступления даты доступны только:

- создание;
- название;
- категория;
- порядок;
- изменение даты на другую будущую дату;
- удаление.

Статус выполнения и приоритет недоступны.

### 13.7. Разбор незавершённых задач

При открытии сегодняшнего дня приложение ищет все задачи прошлых дат со статусом planned.

Для вчерашней задачи доступны:

- «Выполнено вчера»;
- «Перенести на сегодня»;
- «Перенести на другую будущую дату»;
- «Не актуально».

Для задачи старше вчерашней даты доступны:

- «Перенести на сегодня»;
- «Перенести на другую будущую дату»;
- «Не актуально».

Задним числом отметить старую задачу выполненной нельзя, кроме специального действия «Выполнено вчера».

Если пропущено несколько дней, показывается единый блок «Неразобранные задачи», сгруппированный по исходной дате. Блок не мешает пользоваться сегодняшним разворотом и не выполняет действий автоматически.

### 13.8. Удаление

- planned-задачу сегодня или в будущем можно удалить с подтверждением;
- «Не актуально» и «Удалить» — разные операции: «Не актуально» сохраняет задачу в базе со статусом let_go, а «Удалить» физически удаляет planned-задачу и её поисковый документ;
- прошлую задачу удалить нельзя;
- completed-задачу сегодня сначала нужно вернуть в planned;
- перенос не считается удалением;
- удаление задачи-потомка не меняет исторический статус исходной задачи.

## 14. Экран «Неделя»

### 14.1. Границы недели

Неделя всегда с понедельника по воскресенье. День недельного планирования влияет только на уведомление и подсказку, но не на календарные границы. По умолчанию день планирования — воскресенье.

### 14.2. Поля недельного разворота

1. цель недели;
2. почему она важна;
3. критерий успеха;
4. три шага;
5. вероятное препятствие;
6. запасной план;
7. привычки в фокусе.

Все поля необязательны и автосохраняются. Кнопки «Завершить неделю» нет.

### 14.3. Шаг недели

Каждый из трёх шагов имеет:

- порядок 1–3;
- текст;
- необязательную дату внутри этой недели;
- флажок выполнения.

Шаг не является Task, не требует категории и не входит в статистику задач. Если указана дата, шаг показывается на дневном развороте рядом с целью недели. Флажок можно менять только в текущей неделе; прошлое только читается.

### 14.4. Будущие недели

Разрешено открыть любую будущую неделю и заполнить:

- цель;
- три шага и их даты внутри выбранной недели.

Поля «почему», «критерий», «препятствие», «запасной план» и фокус-привычки становятся редактируемыми только с наступлением соответствующей недели. Это сохраняет согласованный минимальный горизонт будущего планирования.

### 14.5. Прошлые недели

После завершения воскресенья недельный разворот блокируется. Разрешён только специальный разбор незавершённой цели.

### 14.6. Разбор цели прошлой недели

Если у прошедшей недели есть цель без результата, при следующем открытии показываются варианты:

- «Достигнута»;
- «Перенести или переформулировать»;
- «Больше не актуальна».

Автоматического переноса нет.

При переносе:

1. Пользователь выбирает текущую или будущую неделю, в которой цель ещё пуста.
2. Получает редактируемый текст, предварительно заполненный старой целью.
3. После подтверждения создаётся новая цель со ссылкой на источник.
4. Старая получает результат transferred.
5. Выбранные незавершённые шаги можно назначить на даты новой недели.

Если целевая неделя уже содержит цель, перенос в неё блокируется с предложением выбрать другую неделю или сначала вручную очистить редактируемую текущую/будущую цель. Существующая цель никогда не перезаписывается автоматически.

Если приложение не открывалось несколько недель, все неразобранные цели показываются списком от новой к старой.

## 15. Цитата дня

### 15.1. Состав библиотеки

В MVP встроено ровно 60 проверенных цитат:

- 24 — юмор или ирония, 40 процентов;
- 18 — прямая мотивация, 30 процентов;
- 18 — философские или глубокие, 30 процентов.

Пользователь не может добавлять, редактировать или удалять встроенный текст. Полный обязательный seed-набор приведён в приложении А этого документа.

На дневном развороте русская редакционная версия показывается полностью: многоточие, line-clamp и обрезка запрещены. Карточка увеличивается по высоте и переносит строки; короткий точный английский фрагмент показывается полностью в окне «Источник».

### 15.2. Что хранится у цитаты

- постоянный ID;
- категория;
- автор;
- русская редакционная версия;
- короткий точный английский фрагмент проверенного издания;
- название произведения;
- год произведения и тип года, если это год первой постановки;
- раздел или локатор внутри произведения;
- URL полного первоисточника;
- признак встроенной записи.

Русский текст в MVP является редакционным переводом команды проекта, а не заявляется как опубликованный перевод конкретного переводчика.

### 15.3. Назначение цитаты на день

- будущая цитата никогда не показывается;
- цитата назначается при первом фактическом открытии сегодняшнего разворота;
- если день не открывался, цитата не назначается и не считается показанной;
- назначенная цитата сохраняется в DailyEntry;
- повторное открытие даты показывает сохранённую цитату;
- в прошлом цитату заменить нельзя.

### 15.4. Колода без повторов

Система ведёт локальную колоду активных цитат.

1. В начале цикла берутся все не скрытые цитаты.
2. Внутри каждой категории ID перемешиваются алгоритмом Fisher–Yates через криптографически стойкий генератор, доступный локально.
3. Категории чередуются так, чтобы на любом длинном префиксе распределение стремилось к 40/30/30.
4. Соседние позиции по возможности не принадлежат одному автору. Если иных авторов нет, это ограничение ослабляется.
5. Каждая цитата появляется не более одного раза за цикл.
6. После исчерпания активной колоды создаётся новый цикл.
7. Избранность не повышает частоту показа.

Вся колода не хранится как источник истины: в базе хранится история показов с номером цикла, что позволяет восстановить оставшиеся кандидаты.

### 15.5. Действия

У цитаты доступны:

- **Другая цитата** — текущая считается показанной, следующая назначается этой же дате и сохраняется;
- **Источник** — локальное окно с автором, произведением, годом, локатором, коротким точным английским фрагментом и ссылкой на полный первоисточник;
- **В избранное / Убрать из избранного**;
- **Больше не показывать**.

«Другая цитата» доступна только сегодня. Количество замен не ограничено, пока есть активные кандидаты.

### 15.6. Скрытие и восстановление

- скрытая цитата немедленно исключается из будущего выбора;
- если скрыта сегодняшняя цитата, автоматически выбирается следующая;
- скрытая цитата остаётся в истории дней, где показывалась раньше;
- в списке «Скрытые» доступно «Восстановить»;
- восстановленная, но ещё не показанная в текущем цикле цитата возвращается в конец текущей колоды;
- если она уже была показана в текущем цикле, вернётся в следующем;
- если скрыты все 60, DailyEntry.quoteId и его поисковый документ очищаются, а блок показывает: «Все цитаты скрыты» и кнопку перехода к восстановлению.

### 15.7. Работа без интернета

Все метаданные источника доступны локально. Внешняя ссылка передаётся системному браузеру без предварительного сетевого запроса приложения. Если интернета нет, стандартную офлайн-страницу показывает браузер; приложение не меняет данные. Если Windows не смогла запустить ссылку, приложение показывает: «Не удалось открыть источник».

## 16. Общая модель привычек

### 16.1. Поддерживаемые типы

| Тип | Кто создаёт | Единица |
|---|---|---|
| Простая привычка | пользователь | один флажок в день |
| Планка | встроенная, не более одного экземпляра | секунды |
| Отжимания | встроенная, не более одного экземпляра | повторения и подходы |
| Вода | встроенная, не более одного экземпляра | миллилитры |

Создавать произвольную числовую, таймерную или водную привычку нельзя.

### 16.2. Состояния

| Состояние | Поведение |
|---|---|
| draft | не хватает цели или расписания; не видна на «Сегодня» |
| active | участвует в расписании и статистике |
| paused | скрыта с ежедневного разворота; уведомления выключены; дни паузы исключены |
| archived | не планируется; доступна в архиве и статистике |

### 16.3. Обязательные параметры

Для активной привычки обязательны:

- название; для встроенной привычки оно фиксировано;
- минимум один конкретный день недели;
- дата начала не раньше даты создания;
- цель: 1 выполнение для простой, секунды для планки, повторения для отжиманий, миллилитры для воды.

Расписание «любые N дней в неделю» не поддерживается.

### 16.4. Количество и названия

- количество простых привычек продуктово не ограничено;
- одновременно не может быть двух неархивированных простых привычек с одинаковым нормализованным названием без учёта регистра;
- названия «Планка», «Отжимания» и «Вода» зарезервированы;
- техническая проверка производительности выполняется минимум на 200 активных простых привычках, хотя интерфейс не должен побуждать создавать столько.

### 16.5. Изменение цели и расписания

Новые параметры действуют с сегодняшней даты и в будущем. Прошлые результаты рассчитываются по версии цели и расписания, которая действовала в соответствующий день.

Пример: повышение цели планки с 60 до 90 секунд сегодня не превращает прошлый выполненный день с 60 секундами в пропуск.

Для этого каждое изменение создаёт HabitRevision:

- предыдущая версия заканчивается вчерашней датой;
- новая начинается сегодня;
- если версия уже была создана сегодня, повторное изменение обновляет сегодняшнюю версию;
- исторические ревизии нельзя редактировать из интерфейса.

### 16.6. Пауза

- пауза начинается сегодня;
- привычка немедленно исчезает из сегодняшнего списка и уведомлений;
- уже сохранённые сегодня измерения остаются в фактических суммах, но день исключается из процента и серии;
- возобновление действует сегодня; день возобновления снова учитывается по расписанию;
- если пауза и возобновление произошли в одну дату, интервал паузы удаляется и дата не исключается;
- старые данные не удаляются.

### 16.7. Архив и восстановление

- привычку с историей нельзя удалить, только архивировать;
- архивирование действует сегодня и не меняет прошлые расчёты;
- архивная привычка видна в фильтрах статистики и в разделе архива;
- дни от архивирования до дня перед восстановлением хранятся отдельным интервалом архива и исключаются из расписания;
- действие «Восстановить» закрывает интервал архива, создаёт новую действующую ревизию с сегодняшней даты и сохраняет всю историю;
- если архивирование и восстановление произошли в один день, пустой интервал архива удаляется;
- черновик или привычку без единой записи можно удалить физически после подтверждения.

### 16.8. Дни вне расписания

На странице привычки пользователь может выбрать «Выполнить дополнительно сегодня», даже если сегодня день отдыха. Такая запись:

- сохраняется в фактическом объёме и общем итоге;
- помечается extra;
- не входит в знаменатель и числитель процента соблюдения расписания;
- не продлевает и не разрывает серию запланированных дней.

### 16.9. Запрет заднего ввода

Ни один тип привычки не разрешает создавать запись за прошлую дату. Исправлять и удалять ошибочные записи можно только до полуночи текущего дня.

## 17. Простая привычка

### 17.1. Создание

Пользователь задаёт:

- название;
- конкретные дни недели;
- дату начала, по умолчанию сегодня.

Цель фиксирована: один раз в запланированный день.

### 17.2. Ежедневное действие

- один флажок;
- сегодня можно отметить и снять отметку;
- повторная отметка не создаёт вторую запись;
- заметок и количества нет;
- вне расписания отметка создаётся только через явное «Выполнить дополнительно сегодня».

### 17.3. Статистика

- календарь состояний;
- текущая серия;
- лучшая серия;
- процент выполнения по расписанию;
- количество обычных выполнений;
- количество дополнительных выполнений.

## 18. Планка

### 18.1. Цель и дневной результат

- цель — положительное целое число секунд от 1 до 600;
- дневная цель достигается суммой всех сохранённых подходов;
- лучший подход показывается отдельно;
- подходов за день может быть несколько.

### 18.2. Запуск

1. Пользователь нажимает «Начать».
2. Идёт фиксированный обратный отсчёт 3, 2, 1.
3. Во время отсчёта доступна «Отмена».
4. После нуля начинается счёт вверх.
5. Паузы нет.
6. Кнопка «Остановить» всегда видна во время активного таймера.

Обратный отсчёт не включается в длительность.

### 18.3. Достижение цели

Когда сумма уже сохранённых сегодня секунд и текущего подхода впервые достигает дневной цели:

- при включённом звуке воспроизводится один мягкий локальный сигнал;
- таймер продолжает идти;
- экран не блокируется;
- сигнал не повторяется в той же сессии.

Если цель была достигнута до запуска нового подхода, сигнал в нём не воспроизводится.

### 18.4. Сохранение

Подход записывается только после явного «Остановить». Длительность:

- вычисляется по разнице системных временных меток;
- округляется вниз до полного количества секунд;
- должна быть от 1 до 599 секунд включительно;
- сохраняется одной транзакцией.

После сохранения показывается результат подхода, сумма дня, лучший подход и прогресс к цели.

### 18.5. Жёсткий предел

Если пользователь не остановил таймер до 10:00:

- ровно при достижении 600 секунд таймер автоматически отменяется;
- подход не сохраняется;
- интерфейс возвращается в исходное состояние;
- показывается нейтральный текст: «Таймер достиг предела 10 минут и был сброшен. Подход не записан».

### 18.6. События отмены

Незавершённый подход не сохраняется и сбрасывается при:

- обновлении страницы;
- закрытии вкладки или браузера;
- переходе на другой маршрут после подтверждения предупреждения;
- завершении фонового процесса;
- перезапуске сервера;
- наступлении полуночи;
- превышении лимита;
- некорректном скачке системного времени назад или вперёд за пределы лимита.

Сворачивание окна, переключение вкладки и блокировка экрана сами по себе подход не отменяют. При возвращении отображается время, рассчитанное по системным часам.

Перед внутренней навигацией показывается: «Активный подход не сохранён. Покинуть страницу и сбросить таймер?»

### 18.7. Исправление текущего дня

Сохранённый сегодня подход можно:

- изменить на целое число от 1 до 599 секунд;
- удалить после подтверждения.

Это предназначено для исправления ошибки и не открывает ввод за прошлые дни.

### 18.8. Статистика планки

- список всех подходов дня;
- сумма дня;
- лучший подход дня;
- сумма недели;
- сумма за всё время;
- дневной график;
- календарь выполнения цели;
- текущая и лучшая серии.

## 19. Отжимания

### 19.1. Цель

- цель — суммарное количество повторений за день;
- положительное целое число от 1 до 100000;
- подходы хранятся отдельно.

### 19.2. Добавление подхода

- пользователь вводит целое число от 1 до 10000;
- ноль, отрицательное, дробь, пустое значение и нечисловой текст не сохраняются;
- после сохранения показываются сумма дня и прогресс к цели;
- отдельного таймера отдыха нет.

### 19.3. Исправление

Сегодня подход можно изменить или удалить. Прошлый подход только читается. Ручной ввод за прошлую дату запрещён.

### 19.4. Статистика отжиманий

- подходы дня;
- лучший подход;
- сумма дня;
- сумма недели;
- сумма за всё время;
- дневной график;
- календарь достижения цели;
- текущая и лучшая серии.

## 20. Вода

### 20.1. Цель

- пользователь самостоятельно вводит положительное целое количество миллилитров;
- допустимый диапазон 1–100000 мл;
- приложение не предлагает медицинскую норму и не оценивает безопасность цели;
- расписание задаётся конкретными днями недели.

### 20.2. Быстрый ввод

Фиксированные кнопки:

- +200 мл
- +250 мл
- +300 мл

Также доступен ввод произвольного положительного целого объёма от 1 до 10000 мл за запись.

### 20.3. Действия

- добавить запись;
- отменить последнюю сегодняшнюю запись;
- изменить любую сегодняшнюю запись;
- удалить любую сегодняшнюю запись;
- просмотреть список времени и объёмов.

Превышение цели разрешено и не вызывает предупреждений. Прошлые записи заблокированы.

### 20.4. Статистика воды

- сумма дня;
- цель дня;
- значения по дням;
- среднее фактическое значение за выбранный период;
- число и доля запланированных завершённых дней, когда цель достигнута;
- общая сумма за период.

## 21. Экран «Привычки»

### 21.1. Список

Разделы:

- Активные
- Черновики
- На паузе
- Архив

Карточка показывает название, тип, расписание, действующую цель, сегодняшнее состояние и действия, допустимые для статуса.

### 21.2. Страница привычки

Содержит:

- действующие параметры;
- редактирование с предупреждением «Изменения действуют с сегодняшнего дня»;
- календарь;
- статистику;
- журнал сегодняшних измерений;
- паузу или возобновление;
- архивирование или восстановление;
- удаление, только если истории нет;
- настройки одного уведомления привычки.

### 21.3. Привычки в фокусе недели

На недельном развороте можно выбрать любые активные привычки как «В фокусе». Это только визуальное выделение; оно не меняет формулы, цель или расписание.

## 22. Экран «Прогресс»

### 22.1. Диапазоны

Ровно три вкладки:

- **Неделя** — с понедельника текущей недели по сегодня;
- **Месяц** — с первого числа текущего месяца по сегодня;
- **Всё время** — от самой ранней пользовательской записи по сегодня.

Произвольный диапазон, предыдущий период и сравнение периодов отсутствуют.

### 22.2. Блок задач

Показывается:

- количество запланированных приоритетных задач;
- количество выполненных приоритетных задач;
- процент выполненных приоритетных задач, если знаменатель больше нуля;
- количество completed-задач по пяти категориям;
- количество дней с выполненным действием «Для себя»;
- количество дней с выполненным действием «Для других»;
- линия настроения только по дням с выбранным значением.

Единого балла продуктивности нет.

### 22.3. Блок привычек

Для каждой привычки:

- процент по расписанию;
- текущая серия;
- лучшая серия;
- календарь;
- типовые измерения из разделов 17–20.

Архивные привычки скрыты по умолчанию, но доступны через переключатель «Показывать архивные».

### 22.4. Пустые состояния

Если данных нет, вместо нуля, который можно принять за неуспех, показывается «Пока нет данных» и краткое объяснение, какое действие создаст первую запись.

## 23. Архив

### 23.1. Разделы

- Календарь
- Дни
- Недели
- Избранные цитаты

Список скрытых цитат доступен из «Настройки → Цитаты».

### 23.2. Месячный календарь

Каждая дата имеет одно из состояний:

- есть запись и утреннее планирование завершено;
- есть запись, но утреннее планирование не завершено;
- «Нет записи»;
- будущая дата.

Цвет не является единственным индикатором: есть значок и доступная текстовая подпись.

### 23.3. Архив дня

Показывает сохранённые:

- цитату;
- ответы;
- благодарность;
- настроение и заметку;
- мысль и настрой;
- главный результат;
- приоритеты и задачи с итоговыми статусами;
- действия для себя и других;
- недельный контекст;
- фактические привычки.

Прошлая запись только читается.

### 23.4. Архив недели

Показывает поля недельного плана, цель, итог цели, три шага и их статусы. Из архива нельзя изменять план.

### 23.5. Избранные цитаты

Список содержит русский текст, автора, источник и действие «Убрать из избранного». Удаление из избранного не скрывает цитату.

## 24. Поиск

### 24.1. Индексируемые данные

Поиск выполняется по:

- названиям задач;
- благодарности;
- мысли дня;
- настрою или намерению;
- ответам на постоянные и меняющиеся вопросы;
- целям недели;
- русскому тексту цитат, английскому проверочному фрагменту и имени автора.

Другие поля в MVP не индексируются.

### 24.2. Поведение

- поиск по подстроке;
- без учёта регистра, включая русский;
- без исправления опечаток;
- без нечёткого и семантического поиска;
- запрос после удаления краевых пробелов должен содержать минимум 2 символа;
- результаты обновляются через 250 мс после ввода;
- сортировка по дате от новых к старым, затем по типу;
- результат содержит дату, тип, фрагмент и подсветку совпадения;
- переход открывает соответствующий день или неделю.

### 24.3. Фильтры

- период: всё время, неделя, месяц, пользовательские «с/по» только как фильтр поиска;
- категория задачи;
- тип записи.

Произвольный период разрешён здесь только для фильтра результатов и не добавляет произвольный период в статистику.

### 24.4. Реализация нормализации

Для каждой индексируемой записи хранится нормализованный поисковый документ:

- Unicode NFKC;
- toLocaleLowerCase с локалью ru-RU;
- исходный текст хранится отдельно;
- поиск выполняется через точное вхождение нормализованной подстроки.

SQLite NOCASE без дополнительной нормализации использовать нельзя, поскольку он не обеспечивает требуемое поведение для русского текста.

## 25. Уведомления и фоновая работа

### 25.1. Общие правила

- все уведомления изначально выключены;
- каждое включается только явным действием пользователя;
- если выбранному локальному адаптеру уведомлений требуется системное разрешение Windows, оно запрашивается только после первого явного включения уведомлений пользователем; собственный toast Electron не должен запрашивать лишнее разрешение;
- уведомления не содержат тексты задач, дневника, целей или привычек;
- пропущенные во время выключенного компьютера или процесса уведомления не показываются позже;
- подавленные уведомления не накапливаются;
- время берётся из локальных часов Windows.

Тексты toast фиксированы:

- утро: «Доброе утро. Выберите главное на сегодня»;
- неделя: «Можно спокойно наметить одну цель недели»;
- обычная привычка: «Время для запланированной привычки»;
- вода: «Можно сделать паузу и выпить воды».

Название привычки и другие личные значения в toast не подставляются.

### 25.2. Утреннее уведомление

Настройки:

- включено или выключено;
- конкретные дни недели;
- время;
- необязательный один повтор через 15 минут.

Если утреннее планирование уже завершено к моменту показа, уведомление подавляется.

### 25.3. Недельное уведомление

- один выбранный день недели;
- одно время;
- одно уведомление без повторов.

По умолчанию используется выбранный день недельного планирования, но уведомление остаётся выключенным.

### 25.4. Уведомление привычки

- не более одного времени для каждой активной привычки;
- работает только в запланированный день;
- не показывается в паузе или архиве;
- подавляется, если дневная цель уже выполнена;
- для простой привычки цель выполнена после отметки;
- для числовой — после достижения суммы.

### 25.5. Уведомления воды

Настройки:

- интервал 60, 90 или 120 минут;
- начало окна;
- конец окна;
- дни определяются расписанием воды.

Правила:

- первое событие — в начале окна;
- последнее не позже конца окна;
- после достижения дневной цели остальные события отменяются;
- в день вне расписания события не создаются;
- превышение цели не создаёт отдельного сообщения.

### 25.6. Тихие часы

- пользователь задаёт начало и конец;
- поддерживается интервал через полночь;
- уведомление внутри тихих часов пропускается, а не переносится;
- после тихих часов накопленные события не показываются.

### 25.7. Кнопки уведомления

| Кнопка | Результат |
|---|---|
| Открыть | открывает сегодня или соответствующую настройку и отменяет повтор события |
| Отложить на 15 минут | создаёт один повтор; на повторном уведомлении кнопка недоступна |
| Закрыть | закрывает событие и отменяет его автоматический повтор |

### 25.8. Системный трей

Меню содержит:

- «Открыть»;
- «Приостановить уведомления» или «Возобновить уведомления»;
- «Выход».

Глобальная пауза действует бессрочно до возобновления, не меняет индивидуальные настройки и не накапливает события.

### 25.9. Автозапуск

- выключен по умолчанию;
- включается в настройках;
- регистрируется только для текущего пользователя Windows;
- не требует прав администратора;
- выключение удаляет только собственную запись автозапуска приложения;
- при автозапуске процесс стартует в фоне, браузер автоматически не открывается.

- переключатель анимации перелистывания;

- избранные;
- скрытые;
- восстановление скрытой;
- количество активных цитат по категориям.

### 26.6. Удаление всех данных

Порядок:

1. Нажать «Удалить все данные».
2. Прочитать предупреждение: действие необратимо, резервной копии нет.
3. Подтвердить первое модальное окно.
4. Ввести ровно «УДАЛИТЬ» без кавычек.
5. Подтвердить второе модальное окно.

В одной транзакции удаляются:

- дневники и ответы;
- задачи и цепочки переносов;
- недельные планы и шаги;
- пользовательские привычки и включённые встроенные трекеры;
- все ревизии, паузы и измерения;
- история показов цитат;
- избранные и скрытые цитаты;
- пользовательские настройки;
- настройки и история уведомлений;
- состояние знакомства;
- поисковый индекс.

После успешной транзакции очищается технический журнал, восстанавливаются настройки по умолчанию, заново проверяются встроенные seed-данные и открывается первоначальное знакомство.

Встроенные 60 цитат и системные вопросы остаются частью приложения. Схема базы и таблица миграций не удаляются.

Если операция завершилась ошибкой, транзакция откатывается, приложение не показывает ложное подтверждение и личные записи остаются доступны.

## 27. Визуальная система

### 27.1. Метафора

Основные экраны дня и недели выглядят как раскрытая бумажная книга. На широком экране видны две страницы; на узком страницы идут вертикально, сохраняя порядок чтения.

### 27.2. Обязательная светлая палитра

| Роль | Цвет | HEX |
|---|---|---|
| Бумага | тёплый молочный | #F7F1E8 |
| Основной | приглушённый шалфейный | #8FA58C |
| Светлый фон | мягкий зелёный | #DDE8DF |
| Акцент | нюдовый | #D8BFAE |
| Основной текст | тёмный зелёно-серый | #2E3A32 |
| Дополнительный акцент | приглушённый терракотовый | #B57F6A |

Терракотовый используется для внимания и ошибок умеренно, а не как наказующий цвет.

### 27.3. Типографика

- книжные заголовки: локальный Georgia или совместимый системный serif;
- элементы управления и основной ввод: Segoe UI или системный sans-serif;
- удалённые веб-шрифты запрещены;
- базовый размер текста не меньше 16 px;
- пользовательский масштаб браузера до 200 процентов не ломает действия.

### 27.4. Анимация

- перелистывание 180–260 мс;
- анимация не должна задерживать сохранение или навигацию;
- при prefers-reduced-motion или выключенной настройке используется мгновенная смена с мягким fade не более 80 мс либо без движения;
- никакой бесконечной декоративной анимации.

### 27.5. Доступность

- целевой уровень WCAG 2.2 AA;
- контраст текста и элементов управления проверяется автоматически;
- все действия доступны клавиатурой;
- видимый focus-ring;
- подписи связаны с полями;
- иконки имеют доступные названия;
- состояния не кодируются только цветом;
- модальные окна удерживают фокус и возвращают его после закрытия;
- графики имеют текстовую таблицу или краткое доступное описание;
- drag-and-drop имеет кнопки «выше/ниже» как клавиатурную альтернативу.

### 27.6. Адаптивность

| Ширина | Компоновка |
|---|---|
| 1200–1920 px | полноценный двухстраничный разворот, максимальная ширина содержимого 1440 px, постоянная навигация |
| 1024–1199 px | компактный двухстраничный разворот с уменьшенными полями |
| 768–1023 px | одна колонка: левая страница, затем правая; навигация над содержимым |
| 360–767 px | одна колонка с полями 16 px; нижнее меню или доступная меню-кнопка |

Горизонтальная прокрутка всей страницы запрещена на ширине 360 px.

Минимальный размер интерактивной области основной кнопки или иконки — 44 × 44 px. Внутренние поля страницы: 32 px при ширине от 1200 px, 24 px при 768–1199 px и 16 px при 360–767 px. Центральный корешок не является элементом управления и не должен перехватывать фокус или указатель.

### 27.7. Нормативные структурные вайрфреймы

Вайрфреймы ниже задают информационную иерархию, порядок блоков и общую компоновку. Они не требуют буквального воспроизведения ASCII-символов, фиксированной высоты блоков или моноширинного шрифта. Цвета, типографика, состояния и анимация определяются разделами 27.2–27.6. Самовольно переносить обязательный блок на другой экран или менять порядок чтения нельзя.

             │ [Источник] [Другая]     │ 2. Задача дня           │

             │ Мысль дня               │ Главный результат дня   │

- «Завершить» располагается после задач дня и остальных дневных блоков правой страницы и остаётся заметным без наказующего акцента;

### 27.8. Обязательные визуальные состояния

Для приёмки должны существовать согласованные состояния одного и того же макета:

- пустой сегодняшний день;
- заполненный сегодняшний день;
- завершённое утреннее планирование;
- прошлый день «Только чтение»;
- будущий день с доступными только задачами;
- ошибка сохранения без потери введённого текста;
- пустой поиск и пустая статистика;
- активная, приостановленная и архивная привычка;
- активный отсчёт и активный таймер планки;
- reduced motion;
- фокус клавиатуры;
- ширины 360, 768, 1024, 1200 и 1920 px.

До появления отдельных графических макетов эти вайрфреймы являются нормативным визуальным ориентиром. Будущий макет может уточнять размеры и декоративные детали, но не отменяет функциональные требования без изменения версии ТЗ.

## 28. Модель данных

### 28.1. Общие соглашения

- первичные ключи прикладных сущностей — UUID v4 в текстовом виде;

## 29. Формулы и алгоритмы

### 29.1. Определение версии привычки для даты

Для даты D выбирается единственная HabitRevision, где:

- effectiveFromDate ≤ D;
- effectiveToDate отсутствует или D ≤ effectiveToDate.

Если такой версии нет, привычка в дату ещё не действовала или уже не действовала.

### 29.2. Запланированный день

Дата D является запланированной, если одновременно:

1. существует действующая ревизия;
2. бит дня недели D включён в scheduleMask;
3. D не входит ни в один HabitExclusionInterval с kind PAUSE или ARCHIVE;
4. D не раньше Habit.startDate.

### 29.3. Выполнение цели

- SIMPLE: существует обычный SimpleHabitLog;
- PLANK: сумма durationSeconds обычных сессий за дату ≥ goalValue ревизии этой даты;
- PUSHUPS: сумма repetitions обычных подходов ≥ goalValue;
- WATER: сумма milliliters обычных записей ≥ goalValue.

Записи isExtra не участвуют в достижении запланированной цели, если сам день не запланирован. На запланированном дне записи создаются с isExtra = false.

### 29.4. Завершённые для расчёта даты

Для мягкой статистики:

- любая запланированная дата раньше сегодня считается завершённой;
- сегодняшняя запланированная дата включается в расчёт, только если цель уже достигнута;
- незавершённый сегодняшний день до полуночи не считается пропуском и не входит в знаменатель;
- будущие даты не входят.

### 29.5. Процент выполнения привычки

completedScheduledDays / elapsedScheduledDays × 100.

Где:

- elapsedScheduledDays — количество завершённых для расчёта запланированных дат;
- completedScheduledDays — среди них даты, где достигнута цель.

Правила отображения:

- один знак после запятой;
- математическое округление half-up;
- если знаменатель 0, показывается «—» и «Пока нет завершённых запланированных дней»;
- паузы, дни отдыха, будущее и дополнительные дни исключены.

### 29.6. Серия

Серия проходит по последовательности запланированных дат, а не по каждому календарному дню.

Текущая серия:

1. Взять последнюю завершённую запланированную дату; если сегодня цель выполнена, взять сегодня.
2. Если эта дата пропущена, текущая серия 0.
3. Идти назад только по предыдущим запланированным датам.
4. Считать подряд выполненные даты до первого пропуска.
5. Дни отдыха и паузы пропускаются и не разрывают серию.
6. Невыполненный сегодняшний день до полуночи серию не разрывает.

Лучшая серия — максимальная длина такого непрерывного участка за всю историю.

### 29.7. Суммы планки

- сумма дня — сумма всех сессий даты, включая extra в фактическом блоке;
- цель дня — только обычные сессии запланированной даты;
- лучший подход — max durationSeconds;
- сумма недели — сумма с понедельника по сегодня;
- всё время — сумма всех сохранённых сессий.

Длительность для показа форматируется:

- меньше 60: N сек;
- 60 и больше: M:SS.

### 29.8. Суммы отжиманий

- дневная сумма — сумма repetitions;
- лучший подход — max repetitions;
- количество подходов — count;
- недельная и общая суммы — простое суммирование соответствующих дат.

### 29.9. Вода

- дневная сумма — сумма milliliters;
- среднее за период — сумма фактических дневных объёмов / число календарных дат периода, в которые была хотя бы одна запись воды;
- если записей нет, среднее не равно нулю, а отображается «—»;
- доля достижения цели использует формулу привычки из 29.5.

### 29.10. Статистика задач

Для выбранного диапазона:

- запланированные приоритеты — число задач с priorityRank не null независимо от итогового статуса;
- выполненные приоритеты — из них status = COMPLETED;
- процент — completed / planned × 100, один знак после запятой;
- выполненные по категории — status = COMPLETED, группировка TaskCategory;
- TRANSFERRED и LET_GO не считаются выполненными;
- «Выполнено вчера» относится к исходной localDate.

### 29.11. Дни для себя и других

- день для себя засчитывается, если selfActionCompletedAt не null;
- день для других засчитывается, если closeActionCompletedAt не null;
- наличие текста без отметки не считается выполнением.

### 29.12. Настроение

Для построения линии используются внутренние значения 1–5 в порядке перечисления Mood. Ось и подсказка всегда показывают слова, а не диагноз, «оценку личности» или средний психологический показатель. Дни без значения пропускаются, нуля не существует.

### 29.13. Границы периодов

- неделя: локальный понедельник 00:00 — сегодня;
- месяц: первое число локального месяца — сегодня;
- всё время: минимальная дата релевантных данных — сегодня;
- будущие части недели и месяца исключаются.

### 29.14. Выбор меняющегося вопроса

Используется тот же принцип колоды без повторов, что у цитат, но отдельный цикл из 10 ID. История вопроса определяется DailyEntry.rotatingPromptId.

## 30. Серверный API

### 30.1. Общие правила

- префикс: /api/v1;
- формат: JSON UTF-8;
- успешный ответ: объект с полем data;
- ошибка: объект error с code, message и необязательным fieldErrors;
- личные тексты не включаются в error.message;
- все мутации проверяют бизнес-дату на сервере;

- version передаётся при обновлении;
- при конфликте version сервер отвечает 409 STALE_VERSION;
- идемпотентные операции принимают Idempotency-Key.

- 200 — чтение или изменение;

## 31. Локальная защита

### 31.1. Модель угроз

Аутентификации по решению пользователя нет. При этом сервер обязан защищаться от случайных или вредоносных запросов с внешних веб-страниц к localhost.

### 31.2. Обязательные меры

- слушать только 127.0.0.1;
- отклонять мутации, если Origin не равен локальному origin приложения;
- выдавать случайный CSRF-токен текущего процесса;
- требовать X-Local-CSRF для POST, PUT, PATCH и DELETE;
- использовать Content-Security-Policy: default-src self; connect-src self; img-src self data; font-src self; object-src none; frame-ancestors none;
- X-Content-Type-Options: nosniff;
- Referrer-Policy: no-referrer;
- запрет встраивания во frame;
- экранирование всего пользовательского текста;
- запрет выполнения сохранённого HTML;
- проверка внешней ссылки цитаты по локальному белому списку seed-URL перед открытием.

### 31.3. Хранение

По утверждённому решению:

- шифрование SQLite не выполняется;
- PIN-кода нет;
- любой человек с доступом к учётной записи Windows и файлу базы потенциально может прочитать записи;
- это ограничение честно указано в README.

## 32. Ошибки, журнал и восстановление процесса

### 32.1. Пользовательские сообщения

Сообщение должно:

- объяснять, что не сохранилось;
- не обвинять пользователя;
- предлагать безопасное следующее действие;
- не показывать stack trace, SQL или путь с личными данными.

Примеры:

- «Не удалось сохранить изменение. Текст остался в поле — попробуйте ещё раз».
- «Эта дата уже закрыта и доступна только для чтения».
- «Приложение уже открыто в другом процессе».

### 32.2. Технический журнал

Разрешённые поля:

- UTC-дата и время;
- уровень;
- код ошибки;
- компонент;
- тип операции;
- безопасный stack trace;
- версия приложения и схемы;
- случайный correlationId.

Запрещено записывать:

- тексты задач;
- благодарности;
- мысли и намерения;
- ответы;
- цели;
- названия пользовательских привычек;
- заметки настроения;
- поисковые запросы;
- полный URL с пользовательскими параметрами.

ID сущности в журнале заменяется односторонним коротким хешем с солью текущего процесса.

### 32.3. Ротация

- максимум 5 файлов;
- максимум 2 МБ каждый;
- старейший удаляется автоматически;
- полный сброс очищает журнал.

### 32.4. Аварийное завершение

- SQLite-транзакции не должны оставаться частично применёнными;
- незавершённый таймер теряется по спецификации;
- после запуска выполняется prisma migrate deploy и integrity_check;
- при неуспешном integrity_check приложение не пытается «починить» личные данные автоматически, а показывает путь к базе и техническую ошибку;
- резервная копия автоматически не создаётся.

## 33. Миграции и seed-данные

### 33.1. Миграции

- каждое изменение схемы оформляется новой миграцией;
- изменять уже применённые миграции нельзя;
- migrate reset в пользовательском запуске запрещён;
- миграция должна сохранять существующие записи;
- потенциально опасное преобразование сначала копирует данные в новую таблицу внутри транзакции, проверяет количество строк и только затем меняет таблицы;
- миграции тестируются на копии синтетической базы предыдущей версии;
- при ошибке запуск прекращается без очистки базы.

### 33.2. Seed

Seed идемпотентен:

- добавляет отсутствующие встроенные записи;
- сверяет контрольную сумму 60 цитат и 13 вопросов;
- не меняет пользовательские состояния избранного и скрытия;
- не меняет сохранённую цитату дня;
- не удаляет неизвестные пользовательские строки;
- фиксирует seedVersion.

Изменять текст утверждённой библиотеки 1.0 без новой версии ТЗ нельзя.

## 34. Согласованность и несколько вкладок

- после успешной мутации вкладка публикует событие через BroadcastChannel;
- другие вкладки инвалидируют соответствующие данные и перечитывают их;
- version защищает от молчаливой перезаписи;
- при 409 текущий пользовательский текст остаётся в поле, показывается «Запись изменилась в другой вкладке» и действия «Загрузить актуальное» или «Повторить с моим текстом»;
- повтор с пользовательским текстом требует нового актуального version;
- операции переноса, сброса, завершения утра и измерений всегда транзакционны и идемпотентны.

## 35. Нефункциональные требования

### 35.1. Производительность

На обычном персональном компьютере, после готовности локального сервера:

- первый содержательный экран — не более 3 секунд;
- переход между уже загруженными разделами — не более 300 мс до визуальной реакции;
- сохранение локальной мутации — медиана не более 200 мс;
- поиск по 100000 SearchDocument — не более 500 мс для типового запроса;
- график до 3650 дневных точек — не более 1 секунды;
- интерфейс не зависает во время расчёта статистики.

Это критерии приёмки на тестовой машине проекта, а не обещание для любого оборудования.

### 35.2. Надёжность

- ни одна составная операция не оставляет частичное состояние;
- повторный запрос с тем же Idempotency-Key не создаёт дубль;
- закрытие браузера не останавливает уведомления;
- завершение процесса из трея корректно закрывает базу;
- пользовательские записи переживают перезапуск и обновление кода;
- системные часы и полночь тестируются через внедряемый Clock, а не реальное ожидание.

### 35.3. Офлайн-режим

После setup.bat и сборки все обязательные сценарии проходят при физически отключённой сети. Исключение — открытие внешней страницы первоисточника.

### 35.4. Совместимость

- Chrome и Edge текущей стабильной версии;
- Windows 10/11;
- мышь, клавиатура и сенсорный ввод;
- масштаб браузера 100–200 процентов;
- системный reduced motion.

Firefox, Safari, Linux, macOS, Android и iOS не входят в обязательную матрицу MVP.

### 35.5. Сопровождаемость

- TypeScript strict без необоснованных any;
- бизнес-формулы находятся в чистых функциях;
- сервер не доверяет клиентским вычислениям;
- UI-тексты собраны в одном локальном словаре;
- даты обрабатываются одной библиотекой и одним DateService;
- API и доменная логика не зависят напрямую от Electron;
- адаптер уведомлений можно заменить без изменения доменных правил.

### 35.6. Конфиденциальность

- нет телеметрии;
- нет crash-reporting во внешнюю сеть;
- нет CDN;
- нет сетевого шрифта;
- нет аналитического cookie;
- нет содержимого записей в журнале;
- нет резервной копии;
- удаление данных необратимо.

### 35.7. Лицензионная гигиена зависимостей

Эти требования являются инженерной проверкой состава проекта, а не юридическим заключением:

- все прямые и транзитивные npm-зависимости фиксируются в package-lock.json;
- у каждой прямой runtime- и development-зависимости должна быть определяемая лицензия и ссылка на официальный репозиторий или пакет;
- пакет с отсутствующей, неопределённой, нестандартной или явно несовместимой лицензией нельзя добавлять молча: требуется решение владельца продукта и при необходимости замена;
- после формирования lock-файла создаётся THIRD_PARTY_NOTICES.md с названием, зафиксированной версией, лицензией и официальным адресом каждой прямой зависимости;
- тексты обязательных лицензий и уведомлений включаются в локальный проект в объёме, требуемом соответствующей лицензией;
- проверка повторяется при каждом изменении package-lock.json;
- перед публичным распространением выполняется отдельная лицензионная и правовая проверка всего поставляемого состава, включая Electron, бинарные runtime-компоненты, изображения, звуки и редакционные русские версии цитат.

## 36. Сценарии использования

### 36.1. Правила описания

Основной актор всех пользовательских сценариев — Пользователь. Если указан Фоновый процесс, он действует только локально. Постусловие является обязательным проверяемым результатом.

### UC-ONB-01 — Открыть приложение впервые

- **Актор:** Пользователь, Фоновый процесс.
- **Предусловия:** база создана, onboardingCompletedAt отсутствует.
- **Основной поток:** start.bat запускает процессы; браузер открывает локальный адрес; система показывает приветствие.
- **Альтернатива:** при незавершённом знакомстве открывается сохранённый шаг.
- **Постусловие:** никакие привычки, планы и задачи не созданы автоматически.

### UC-ONB-02 — Выбрать день планирования

- **Предусловия:** открыт соответствующий шаг.
- **Поток:** пользователь выбирает один день недели; система сохраняет черновик; пользователь продолжает.
- **Альтернатива:** «Пропустить» сохраняет воскресенье.
- **Постусловие:** weeklyPlanningWeekday содержит 1–7.

### UC-ONB-03 — Задать первую цель недели

- **Предусловия:** открыта текущая календарная неделя.
- **Поток:** пользователь вводит цель до 500 символов; продолжает; система сохраняет её в текущий WeeklyPlan.
- **Альтернатива:** пустое поле или пропуск не создаёт содержательную цель.
- **Постусловие:** цель видна на сегодняшнем развороте либо отсутствует.

### UC-ONB-04 — Включить встроенные трекеры

- **Поток:** пользователь независимо выбирает планку, отжимания и/или воду; для каждого задаёт цель и дни; сохраняет.
- **Валидация:** цель и минимум один день обязательны для active.
- **Альтернатива:** выбранный, но недонастроенный трекер сохраняется draft; не выбранный не создаётся.
- **Постусловие:** у каждого типа не более одного встроенного Habit.

### UC-ONB-05 — Добавить простую привычку

- **Поток:** пользователь вводит название и выбирает дни; сохраняет.
- **Альтернатива:** пропуск ничего не создаёт; неполная конфигурация создаёт draft только после явного «Сохранить черновик».
- **Ошибка:** дубликат нормализованного названия возвращает понятное сообщение.
- **Постусловие:** валидная привычка active и доступна по расписанию.

### UC-ONB-06 — Пропустить всё знакомство

- **Поток:** пользователь нажимает «Пропустить знакомство» и подтверждает переход.
- **Постусловие:** onboardingCompletedAt заполнено; день планирования — воскресенье; привычек и недельной цели нет; открыт сегодняшний день.

### UC-ONB-07 — Завершить знакомство

- **Поток:** система валидирует каждый сохранённый объект, применяет изменения транзакционно, ставит onboardingCompletedAt и открывает «Сегодня».
- **Ошибка:** при сбое знакомство остаётся незавершённым, черновик не теряется.
- **Постусловие:** повторный запуск больше не показывает знакомство.

### UC-NAV-01 — Открыть сегодняшнюю дату

- **Предусловия:** знакомство завершено.
- **Поток:** пользователь запускает приложение или нажимает «Сегодня»; система определяет локальную дату и загружает разворот.

### UC-NAV-02 — Открыть прошлый день

- **Поток:** пользователь выбирает прошлую дату; система показывает архивный разворот.

## 37. Критерии приёмки

Формат: «Дано / Когда / Тогда». Каждый критерий должен пройти до итоговой приёмки. Обязательность автоматизации определяется приоритетами раздела 38: P0 автоматизируется до готовности личного MVP, P1 может быть проверен вручную и автоматизирован на этапе полировки. Визуальные проверки по определению допускают ручную приёмку владельцем продукта.

| ID | Дано | Когда | Тогда |
|---|---|---|---|

## 38. План тестирования

### 38.0. Приоритеты проверок

Уровень относится к сроку автоматизации, а не к обязательности функции:

- **P0 — блокирует готовность личного MVP.** Автоматизируются критические правила дат, неизменяемость прошлого, сохранение данных, основные мутации, миграции, полный сброс, безопасность localhost, локальный запуск и ключевые расчёты привычек. Основной пользовательский маршрут дополнительно проходит вручную владельцем.
- **P1 — полировка личной версии.** Функция должна работать и пройти соответствующий AC вручную, но полная автоматизация расширенных комбинаций, визуальная регрессия всех экранов и полный скринридерный прогон могут быть завершены после первого рабочего MVP.
- **P2 — до публичного распространения.** Упаковка для нетехнического пользователя, code signing, полная матрица Windows-конфигураций, расширенный аудит доступности и дистрибуция. P2 не входит в MVP 1.2.

Минимальный P0-набор включает:

1. Все модульные случаи 38.1, относящиеся к датам, правам past/today/future, ревизиям, процентам, сериям, таймеру, уведомлениям и идемпотентности.
2. Интеграционные проверки запрета прошлого, переноса задач, привычек, reset, миграций, CSRF/Origin, optimistic version и транзакционного SearchDocument.
3. E2E-сценарии 1–4 и 8–11 из 38.3.
4. Критические проверки фонового процесса: единственный экземпляр, health-check, запуск и остановка дочернего процесса, офлайн, закрытый браузер, безопасный выход.
5. Проверку миграций 38.8.
6. Ручное прохождение владельцем пустого и заполненного сегодняшнего разворота на 360 и 1200 px только клавиатурой и мышью.

Оставшиеся перечисленные проверки относятся к P1, если конкретный пункт явно не назван P0. Все обнаруженные дефекты потери данных, разблокировки прошлого, внешней передачи личных данных или необратимого частичного состояния автоматически имеют приоритет P0.

### 38.1. Модульные тесты

Обязательно покрыть:

- вычисление businessDate;
- начало и конец недели;
- права past/today/future;
- нормализацию русской строки;
- валидацию всех лимитов;
- scheduleMask;
- выбор HabitRevision;
- пересекающиеся ревизии и паузы;
- выполнение всех четырёх типов привычек;
- процент при нулевом знаменателе;
- текущую и лучшую серию с днями отдыха, паузой, extra и текущим днём;
- сумму и максимум подходов;
- границу планки 599/600;
- колоды цитат и вопросов;
- распределение цитат 24/18/18;
- смену рангов;
- дедупликацию Idempotency-Key;
- тихие часы через полночь;
- расчёт следующего уведомления;
- отсутствие догоняющих событий.

Числовой процент покрытия не является блокирующим показателем личного MVP. Отчёт покрытия сохраняется для контроля, но готовность определяется прохождением всех перечисленных P0-ветвей и граничных значений. UI-обвязка не должна искусственно повышать показатель.

### 38.2. Интеграционные тесты

На временной SQLite-базе:

- CRUD сегодняшнего дня;
- запрет прошлого и ограничение будущего;
- частичный UNIQUE приоритетов;
- перенос задачи одной транзакцией;
- разбор вчера;
- перенос недельной цели;
- ревизия привычки;
- пауза и восстановление;
- редактирование сегодняшних измерений;
- обновление SearchDocument в одной транзакции;
- QuoteDisplay и замена;
- reset с откатом на искусственной ошибке;
- CSRF и Origin;
- optimistic version 409;
- миграция предыдущей схемы.

### 38.3. Сквозные тесты Playwright

Минимальный набор:

1. **P0.** Чистый запуск → пропуск знакомства → сегодняшний разворот.
2. **P0.** Одна задача дня № 1 → действие «Завершить» → перезапуск → «Завершено» и данные на месте.
3. **P0.** Будущая задача → искусственная смена даты → назначение приоритета.
4. **P0.** Полночь с активной планкой → сброс и блокировка прошлого.
5. **P1.** Вчерашняя и старая задачи → разные наборы действий.
6. **P1.** Текущая и будущая недели.
7. **P1.** Полный цикл цитат на сокращённой тестовой колоде.
8. **P0.** Создание, изменение, пауза, архив и восстановление привычки.
9. **P0.** Планка, отжимания и вода.
10. **P0.** Поиск русской подстроки и фильтры.
11. **P0.** Полный сброс.
12. **P1.** Основной маршрут на 360, 768, 1024, 1200 и 1920 px.

Clock и генератор случайности в тестах внедряются через интерфейсы, чтобы результаты были детерминированы.

### 38.4. Тесты фонового процесса

- единственный экземпляр;
- запуск/остановка Next child process;
- готовность порта;
- меню трея;
- запуск без браузера при автозагрузке;
- показ toast при закрытом браузере;
- Open, Snooze, Close;
- тихие часы;
- глобальная пауза;
- выключенный процесс во время расписания;
- безопасное завершение.

### 38.5. Проверка офлайн

На тестовой машине после setup.bat:

1. Отключить Wi-Fi/Ethernet.
2. Очистить DNS-кэш необязательно; тест не должен зависеть от него.
3. Запустить start.bat.
4. Пройти дневник, задачи, неделю, все привычки, прогресс, архив и поиск.
5. Убедиться по инструментам браузера, что внешних запросов нет.
6. Нажать внешний источник и проверить только корректную обработку отсутствия сети.

### 38.6. Доступность

- **P0:** ручная клавиатурная проверка основного утреннего маршрута, видимый фокус, отсутствие ловушки фокуса, 200-процентный масштаб и доступная кнопочная альтернатива drag-and-drop;
- **P1:** автоматический axe-core для всех основных экранов, скринридерная проверка названий элементов, контраст всех фактически используемых пар токенов и reduced motion во всех переходах;
- **P2:** расширенный аудит WCAG 2.2 AA перед публичным распространением.

### 38.7. Визуальная регрессия

Полный автоматический набор этого подраздела имеет приоритет P1. До его автоматизации владелец вручную принимает пустой и заполненный сегодняшний разворот на 360 и 1200 px по вайрфреймам 27.7; эта минимальная проверка является P0.

Эталонные снимки:

- пустой и заполненный сегодняшний разворот;
- завершённое утреннее планирование;
- будущий и прошлый день;
- неделя;
- карточки четырёх типов привычек;
- графики и пустые состояния;
- архив;
- модальные окна;
- уведомление;
- ширины 360, 768, 1200 и 1920 px.

Допустимое отличие пикселей задаётся тестовой инфраструктурой, но текстовые переполнения и горизонтальная прокрутка недопустимы.

### 38.8. Проверка миграций

В репозитории хранится только синтетическая fixture-база предыдущей версии без личных данных. Для каждой новой миграции CI или локальный test-скрипт:

1. Копирует fixture во временный каталог.
2. Применяет migrate deploy.
3. Проверяет schemaVersion.
4. Проверяет контрольные суммы тестовых строк.
5. Запускает integrity_check.

## 44. Управление изменениями и неоднозначностями

### 44.1. Что разработчик решает самостоятельно

Без отдельного вопроса владелец делегирует разработчику решения, которые не меняют наблюдаемое пользовательское поведение, данные или границы MVP, например:

- внутреннее имя модуля, функции или CSS-класса;
- разбиение кода на файлы;
- эквивалентную замену несовместимой библиотеки при сохранении API продукта и всех AC;
- техническую оптимизацию запроса без изменения результата;
- исправление очевидной опечатки в комментарии или документации.

Такое решение должно оставаться проверяемым тестами и не может отменять явное требование.

### 44.2. Когда необходимо согласование владельца

Разработчик обязан остановить затронутую часть работы и запросить решение, если обнаружено хотя бы одно условие:

- два обязательных требования дают разные результаты для одного состояния;
- нет правила для пограничного случая, а выбор будет виден пользователю или изменит сохранённые данные;
- требуется добавить функцию из раздела 3.2;
- требуется удалить, ослабить или отложить P0-требование;
- меняются тексты вопросов, цитат, мягкой мотивации, категории или формулы;
- возникает потенциально разрушительная миграция;
- требуется внешняя сеть, облако, передача личных данных или новая лицензия с неясными условиями.

### 44.3. Приоритет чтения требований

Внутри одной версии разработчик проверяет источники в следующем порядке:

1. Явное правило состояния, безопасности данных или запрета.
2. AC раздела 37.
3. Функциональные правила, формулы, модель данных и API разделов 9–35.
4. UC раздела 36.
5. Общие продуктовые принципы и вайрфреймы.

Этот порядок помогает найти более конкретное правило, но не разрешает настоящее противоречие молча. Если два пункта одного или разных уровней несовместимы, решение принимает владелец продукта.

concept.md, переписка и старые прототипы не участвуют в этой иерархии и не используются для отмены требования tz.md.

### 44.4. Порядок фиксации решения

1. Разработчик формулирует спорный случай, приводит связанные пункты ТЗ и описывает влияние вариантов без личных данных.
2. Он предлагает один рекомендуемый вариант, явно отделяя рекомендацию от уже подтверждённого требования.
3. Владелец продукта выбирает решение.
4. Если меняется наблюдаемое поведение, tz.md получает новую версию и запись в 1.3; синхронно обновляются затронутые правила, UC, AC, тесты и матрица трассировки.
5. Код для спорного поведения изменяется только после фиксации решения. Уже безопасно выполненная независимая работа может продолжаться.

Устное или чат-сообщение считается промежуточным до переноса принятого решения в новую версию tz.md. Последняя сохранённая версия tz.md остаётся единственным нормативным источником.

# Приложение Б. Ненормативные справочные источники продуктовых решений

Эти публикации не являются медицинскими рекомендациями и не используются для автоматической оценки пользователя. Они объясняют, почему продукт фиксирует наблюдаемый прогресс, ограничивает число целей и допускает индивидуальную длительность ритуала:

- [Harkin et al., Does Monitoring Goal Progress Promote Goal Attainment?](https://pubmed.ncbi.nlm.nih.gov/26479070/) — метаанализ связи мониторинга прогресса с достижением целей.
- [Lally et al., How are habits formed: Modelling habit formation in the real world](https://onlinelibrary.wiley.com/doi/abs/10.1002/ejsp.674) — исследование различий в сроках формирования привычек; продукт поэтому не обещает фиксированное число дней.
- [Locke and Latham, Building a practically useful theory of goal setting and task motivation](https://doi.org/10.1037/0003-066X.57.9.705) — обзор теории постановки целей.

Функциональные требования настоящего ТЗ определяются подтверждёнными решениями пользователя, а не автоматически выводятся из этих публикаций.
